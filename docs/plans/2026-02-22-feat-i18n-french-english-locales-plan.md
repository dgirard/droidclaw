# feat: Add i18n with French and English locales

## Overview

Internationalize the entire DroidClaw application with two locales: **English (default)** and **French**. The scope covers all three layers: UI strings, tool output strings (`forUser`), and agent/system prompt strings. The implementation uses Flutter's official `flutter_localizations` + ARB files approach with code generation.

The main architectural challenge is the **dual-isolate constraint**: the service isolate (foreground service for Telegram + crons) has no `BuildContext`, so localized strings must be accessible without Flutter's `Localizations.of(context)` widget layer.

## Problem Statement / Motivation

The codebase currently has a **mixed-language problem**:
- UI strings are in English
- Weather WMO descriptions are in French (`Ciel degagé`, `Pluie légère`)
- Transit labels are in French (`correspondance`, `Durée`, `Départ`)
- Datetime tool hardcodes `fr_FR` locale

This is inconsistent and blocks any future locale support. With ~300 translatable strings spread across 40+ files, a systematic i18n approach is needed.

## Proposed Solution

### Architecture: Context-Free Localization

Flutter's `flutter_localizations` + `intl` code generation produces **pure Dart classes** with no platform channel dependency. This means the generated `AppLocalizations` class works in both isolates.

The key design decision: **avoid `Localizations.of(context)`** as the primary access pattern. Instead, use a **static singleton accessor** that works everywhere:

```dart
// Access pattern — works in both isolates, no BuildContext needed
final l = AppLocalizations.of(locale);  // Static factory, pure Dart
l.settingsTitle  // → "Settings" or "Paramètres"
```

### Locale Resolution Chain

```
1. User selects locale in Settings (or "System default")
2. Main isolate: stores in SharedPreferences + rebuilds MaterialApp locale
3. Service isolate: reads from SharedPreferences on init/reload
4. Tools receive locale via constructor injection (same pattern as API keys)
5. Agent system prompt adapts response language instruction based on locale
```

## Technical Approach

### Phase 1: Foundation — ARB setup + generated code

**Files to create:**

| File | Purpose |
|------|---------|
| `lib/l10n/app_en.arb` | English strings (~300 entries) — source of truth |
| `lib/l10n/app_fr.arb` | French translations (~300 entries) |
| `lib/l10n/l10n.dart` | Convenience export + static accessor helper |
| `l10n.yaml` | Flutter l10n configuration |

**Files to modify:**

| File | Change |
|------|--------|
| `pubspec.yaml` | Add `flutter_localizations` SDK dep, enable `generate: true` |
| `lib/app.dart` | Add `localizationsDelegates`, `supportedLocales`, `locale` from config |
| `lib/shared/constants.dart` | Add `localeKey` constant for SharedPreferences |
| `lib/core/config/app_config.dart` | Add `locale` field (`'en'`, `'fr'`, `'system'`) |

**`l10n.yaml` configuration:**

```yaml
arb-dir: lib/l10n
template-arb-file: app_en.arb
output-localization-file: app_localizations.dart
output-class: AppLocalizations
synthetic-package: false
output-dir: lib/l10n/generated
nullable-getter: false
```

Setting `synthetic-package: false` places generated code in `lib/l10n/generated/` — importable from anywhere, including service isolate code in `lib/core/`.

**Static accessor pattern in `lib/l10n/l10n.dart`:**

```dart
import 'generated/app_localizations.dart';

export 'generated/app_localizations.dart';

/// Get localized strings without BuildContext.
/// Works in both main isolate and service isolate.
AppLocalizations tr(String languageCode) {
  return lookupAppLocalizations(Locale(languageCode));
}
```

The `lookupAppLocalizations` function is generated by `flutter gen-l10n` and is a pure Dart function that returns the correct `AppLocalizations` subclass for a locale. No `BuildContext` needed.

### Phase 3: Tool output string extraction (~120 strings)

Tools need locale injected via constructor, following the existing API key pattern.

**Locale injection pattern:**

```dart
class WeatherTool extends Tool {
  final String locale;  // 'en' or 'fr'
  WeatherTool({this.locale = 'en'});

  // In execute():
  final l = tr(locale);
  return ToolResult.dual(
    forLLM: '...',  // Always English — LLM reasoning language
    forUser: l.weatherClearSky,  // Localized for display
  );
}
```

### Phase 4: Agent/notification strings + locale propagation

**Agent strings:**

| File | Change |
|------|--------|
| `lib/core/agent/context_builder.dart` | Add locale-aware instruction: `"Respond in French."` / `"Respond in English."` appended to system prompt. The system prompt itself stays English (for LLM reasoning). |
| `lib/core/agent/agent_loop.dart` | Summarization prompt stays English (LLM instruction). Error messages to user → localized. |
| `lib/providers/chat_provider.dart` | `'No LLM provider configured...'` → localized |
| `lib/features/telegram/telegram_bot_manager.dart` | `'This bot is private.'`, error messages → localized |

**Notification strings:**

| File | Change |
|------|--------|
| `lib/core/services/background_task_handler.dart` | Notification titles/text → localized via `tr(locale)` |
| `lib/providers/background_service_provider.dart` | Channel names, notification text → localized. Cache locale in SharedPreferences alongside API keys. |

**Service isolate locale propagation:**

Follow the existing API key caching pattern in `_cacheSecretsForService()`:

```dart
// In BackgroundServiceNotifier._cacheSecretsForService()
final locale = config.locale;  // 'en', 'fr', or 'system'
final resolved = locale == 'system' ? _resolveSystemLocale() : locale;
await prefs.setString(AppConstants.cachedLocaleKey, resolved);
```

In `BackgroundTaskHandler`:
```dart
final locale = prefs.getString(AppConstants.cachedLocaleKey) ?? 'en';
```

**Locale change flow:**

```
User selects "French" in Settings
  → AppConfig.locale = 'fr'
  → appConfigProvider invalidated
  → MaterialApp rebuilds with Locale('fr')
  → toolRegistryProvider rebuilds (tools get new locale)
  → _cacheSecretsForService() caches 'fr' in SharedPreferences
  → Service isolate picks up on next cron check or reload
```

| File | Change |

## Strings NOT to Localize

These must stay in English regardless of locale:

- **Tool `name` fields** — snake_case identifiers (`web_search`, `get_transit`)
- **Tool `description` and `parameters` JSON Schema** — sent to LLM for tool selection
- **`ToolResult.forLLM`** — consumed by LLM for reasoning
- **Summarization prompt** in `agent_loop.dart` — LLM instruction
- **System prompt body** in `context_builder.dart` — LLM instruction (only the response language hint changes)
- **Log messages** (`_log('[DroidClaw] ...')`) — developer debugging
- **SharedPreferences keys** — internal constants
- **API error messages from external services** — pass through as-is

## Dependencies & Risks

### Dependencies

- `flutter_localizations` (Flutter SDK — already available, just needs enabling)
- `intl` package (likely already a transitive dependency)

### Risks

| Risk | Mitigation |
|------|-----------|
| ~300 strings across 40+ files — large mechanical change | Phase the work: foundation first, then UI, then tools, then agent |
| French translations quality | Developer (native French speaker) writes translations directly |
| Locale change not reaching service isolate immediately | Cache in SharedPreferences + reload on next `onRepeatEvent` cycle. Send `reload_locale` action if service is running. |
| `lookupAppLocalizations` function not exported by code gen | Verify with `flutter gen-l10n` output. Fallback: instantiate `AppLocalizationsEn()` / `AppLocalizationsFr()` directly. |
| Breaking existing weather/transit French strings during migration | Extract current French strings into `app_fr.arb` first, then add English equivalents |

## Implementation Order

```
Phase 1: Foundation (l10n.yaml, ARB files, pubspec, app.dart)
  ↓
Phase 2: UI strings (features/*.dart → AppLocalizations.of(context))
  ↓
Phase 3: Tool outputs (tools/*.dart → tr(locale) via constructor injection)
  ↓
Phase 4: Agent/notifications (context_builder, agent_loop, background handler)
  ↓
Phase 5: Settings UI (locale selection screen)
  ↓
Phase 6: Cron display strings
```

Phases 2 and 3 are the bulk of the work (~280 strings). Phase 1 and 5 are the architectural pieces. Phase 4 and 6 are small.
